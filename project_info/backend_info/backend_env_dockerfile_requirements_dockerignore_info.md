# backend Infrastructure & Configuration Files Documentation

## Overview
This document covers the configuration and deployment infrastructure files for the SecureGuard Pro backend. These files define environment variables, Python dependencies, Docker containerization, and build-time exclusions. Together, they enable local development, CI/CD testing, and production deployment with a single command.

**Total Files**: 4  
**Key Components**: Environment config, Python dependencies, Docker build, ignore patterns

## File: .dockerignore

### Purpose
Specifies files and directories that Docker should NOT copy into the container image during the build process. Similar to .gitignore for Docker builds. Reduces image size and avoids copying unnecessary/sensitive files.

### Content

```
# Python
__pycache__/
*.pyc
*.pyo
*.pyd
.Python
*.egg-info/

# Virtual environment — never copy this into Docker
# Docker installs its own packages from requirements.txt
venv/
.venv/
env/

# Environment files — injected at runtime, not baked into image
.env

# Dev/editor files
.git/
.gitignore
*.md
DEVLOG.md

# Test files
tests/
pytest_cache/
.coverage
```

### Line-by-Line Explanation

#### Python Bytecode & Cache (Lines 1-7)
```
# Python
__pycache__/
*.pyc
*.pyo
*.pyd
.Python
*.egg-info/
```

**Purpose**: Remove compiled Python artifacts that are generated on each run.

- `__pycache__/`: Directory containing compiled .pyc files (auto-generated)
- `*.pyc`: Compiled Python modules (machine code)
- `*.pyo`: Optimized compiled Python (pre-3.9 format)
- `*.pyd`: Windows Python extension modules
- `.Python`: Virtual environment marker
- `*.egg-info/`: Package metadata (generated by setuptools)

**Effect**: Reduces image size; these are regenerated at runtime if needed.

---

#### Virtual Environments (Lines 9-13)
```
# Virtual environment — never copy this into Docker
# Docker installs its own packages from requirements.txt
venv/
.venv/
env/
```

**Purpose**: Exclude local development virtual environments; Docker creates its own isolated environment.

**Why Critical**: 
- Local venv is OS-specific (e.g., Linux wheels won't work on Windows and vice versa)
- Docker installs fresh from PyPI for the container's OS
- Copying venv wastes image space (hundreds of MB)

---

#### Environment Files (Lines 15-16)
```
# Environment files — injected at runtime, not baked into image
.env
```

**Purpose**: Prevent baking sensitive .env file into the image.

**Security Implication**:
- `.env` contains API keys, database credentials, secrets
- If baked into image, those secrets are visible to anyone with access to the image
- Use docker-compose.yml or .env.production injected at runtime instead

---

#### Dev/Editor Files (Lines 18-22)
```
# Dev/editor files
.git/
.gitignore
.md
DEVLOG.md
```

**Purpose**: Exclude development artifacts from production image.

- `.git/`: Git history (not needed in container; wastes ~100MB+)
- `.gitignore`: Developer convention file (not needed at runtime)
- `*.md`: Documentation (not needed in container)
- `DEVLOG.md`: Development notes (not needed in container)

---

#### Test Files (Lines 24-27)
```
# Test files
tests/
pytest_cache/
.coverage
```

**Purpose**: Exclude testing infrastructure from production container.

- `tests/`: Test source code (not needed in production)
- `pytest_cache/`: Test cache directory
- `.coverage`: Code coverage reports

---

### Impact on Image Size

**Example**: With and without .dockerignore:

```
Without .dockerignore:
- venv/ copied: +500 MB
- .git/ copied: +100 MB
- __pycache__ copied: +50 MB
- Total: ~650 MB overhead
Final image: ~1.2 GB

With .dockerignore:
- Excluded all above
Final image: ~550 MB (57% reduction)
```

## File: .env.example

### Purpose
Template file showing all required and optional environment variables. Developers copy this to `.env` and fill in their actual values. Serves as documentation of what configuration the app needs.

**Note**: `.env.example` is committed to git; `.env` is git-ignored (contains secrets).

### Content

```
# Supabase - get these from your Supabase dashboard → Settings → API
SUPABASE_URL=https://your-project-ref.supabase.co
SUPABASE_ANON_KEY=your-anon-key-here
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key-here

# App
APP_ENV=development
APP_HOST=0.0.0.0
APP_PORT=8000

# CORS - frontend URL allowed to talk to this backend
# Both ports covered: 5173 is Vite default, 8080 is fallback when 5173 is taken
CORS_ORIGINS=http://localhost:5173,http://localhost:8080

# GitHub OAuth App credentials
# Get these from: github.com → Settings → Developer settings → OAuth Apps
GITHUB_CLIENT_ID=your_github_client_id_here
GITHUB_CLIENT_SECRET=your_github_client_secret_here
GITHUB_CALLBACK_URL=http://localhost:8000/teams/github/callback
```

### Configuration Variables

#### Supabase (Lines 1-4)

**SUPABASE_URL** (required)
```
SUPABASE_URL=https://your-project-ref.supabase.co
```
- Project URL from Supabase dashboard
- Format: `https://[PROJECT-REF].supabase.co`
- Example: `https://abcdefgh.supabase.co`

**SUPABASE_ANON_KEY** (required)
```
SUPABASE_ANON_KEY=your-anon-key-here
```
- Public key for frontend/anonymous requests
- Subject to Row-Level Security (RLS) policies
- Safe to expose in frontend code

**SUPABASE_SERVICE_ROLE_KEY** (required)
```
SUPABASE_SERVICE_ROLE_KEY=your-service-role-key-here
```
- Admin key; bypasses RLS
- **NEVER expose to frontend**
- Used only by backend (server-side operations)
- Stored securely in backend .env (git-ignored)

---

#### App Configuration (Lines 6-9)

**APP_ENV** (optional; default: development)
```
APP_ENV=development
```
- Development mode: API docs enabled at /docs, verbose logging
- Production mode: API docs disabled, optimized for security

**APP_HOST** (optional; default: 0.0.0.0)
```
APP_HOST=0.0.0.0
```
- Host to bind to inside container
- `0.0.0.0` = listen on all network interfaces (required in Docker)

**APP_PORT** (optional; default: 8000)
```
APP_PORT=8000
```
- Port to listen on
- Published to host via docker-compose.yml

---

#### CORS Configuration (Lines 11-13)

**CORS_ORIGINS** (optional; default: http://localhost:5173)
```
CORS_ORIGINS=http://localhost:5173,http://localhost:8080
```
- Comma-separated list of allowed frontend origins
- Browsers block requests from unlisted origins
- Example with multiple origins: `http://localhost:5173,https://myapp.com,https://app.myapp.com`

**Why Needed**:
- Frontend (localhost:5173 or 8080) calls API
- Browser enforces same-origin policy
- Backend must explicitly allow frontend origin in CORS headers

---

#### GitHub OAuth (Lines 15-19)

**GITHUB_CLIENT_ID** (optional; for GitHub integration)
```
GITHUB_CLIENT_ID=your_github_client_id_here
```
- OAuth client ID from GitHub App
- Get from: github.com → Settings → Developer settings → OAuth Apps

**GITHUB_CLIENT_SECRET** (optional; for GitHub integration)
```
GITHUB_CLIENT_SECRET=your_github_client_secret_here
```
- OAuth client secret (keep secure; never commit)

**GITHUB_CALLBACK_URL** (optional; for GitHub integration)
```
GITHUB_CALLBACK_URL=http://localhost:8000/teams/github/callback
```
- Redirect URL after GitHub OAuth login
- Must match registered URL in GitHub app settings
- Local dev: `http://localhost:8000/teams/github/callback`
- Production: `https://api.myapp.com/teams/github/callback`

## File: Dockerfile

### Purpose
Docker build configuration that packages the Python FastAPI application into a lightweight, production-ready container image. Uses multi-stage build to minimize final image size.

**Key Principles**:
- Multi-stage build (builder + runtime)
- Slim Python image (50 MB vs 900 MB full)
- Layer caching for fast rebuilds
- Minimal dependencies in final image

### Content & Analysis

```dockerfile
# ---------------------------------------------------------------------------
# Stage 1: Builder
# ---------------------------------------------------------------------------
FROM python:3.11-slim AS builder

WORKDIR /app

COPY requirements.txt .

RUN pip install --no-cache-dir --prefix=/install -r requirements.txt


# ---------------------------------------------------------------------------
# Stage 2: Runtime
# ---------------------------------------------------------------------------
FROM python:3.11-slim

WORKDIR /app

COPY --from=builder /install /usr/local

COPY app/ ./app/

ENV APP_HOST=0.0.0.0
ENV APP_PORT=8000
ENV APP_ENV=production

EXPOSE 8000

CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

### Stage 1: Builder (Lines 1-20)

**Purpose**: Install dependencies without build tools; keep final image clean.

```dockerfile
FROM python:3.11-slim AS builder
```

- `python:3.11-slim`: Lightweight Python 3.11 image (~50 MB)
  - Contains Python, pip, basic tools
  - No full build toolchain
  - `slim` = Debian slim (minimal OS)

**Alternative**: `python:3.11-full` would be ~900 MB (includes gcc, build tools, etc.)

```dockerfile
WORKDIR /app
```

- Sets working directory inside container
- All subsequent commands run in /app
- Equivalent to `cd /app` on your machine

```dockerfile
COPY requirements.txt .
```

- Copy requirements.txt from host to container
- `.` = current WORKDIR (/app/requirements.txt)

**Why first**: Docker caches layers. If requirements.txt hasn't changed, `RUN pip install` is skipped on rebuild (saves time).

```dockerfile
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt
```

- `--no-cache-dir`: Don't store pip cache (~100 MB saved)
- `--prefix=/install`: Install to /install directory (not system Python)
- `-r requirements.txt`: Install all packages listed

**Effect**:
- All packages installed to `/install` directory
- Builder stage now contains: Python + packages in /install
- Later, we copy only /install to runtime stage (ignore builder's everything else)

---

### Stage 2: Runtime (Lines 23-63)

**Purpose**: Clean image with only application code and dependencies (no build tools).

```dockerfile
FROM python:3.11-slim

WORKDIR /app
```

- Fresh slim Python image (no builder artifacts)
- Working directory: /app

```dockerfile
COPY --from=builder /install /usr/local
```

- Copy packages from builder stage's `/install` to `/usr/local`
- `/usr/local` is where pip normally installs packages
- Result: All dependencies available in runtime container

**Effect**: 
- Builder stage discarded after copy (saves ~200 MB)
- Runtime stage only contains: Python + app packages (no build tools)

```dockerfile
COPY app/ ./app/
```

- Copy application source code
- `app/` from host → `./app/` in container
- Copies: main.py, models/, routers/, services/, config.py, etc.

```dockerfile
ENV APP_HOST=0.0.0.0
ENV APP_PORT=8000
ENV APP_ENV=production
```

- Set environment variables inside container
- `APP_HOST=0.0.0.0`: Listen on all interfaces (required for Docker)
- `APP_PORT=8000`: Listen on port 8000
- `APP_ENV=production`: Production mode (disable docs, optimize)

**Override**: docker-compose.yml can override these with different values.

```dockerfile
EXPOSE 8000
```

- **Documentation only** — doesn't actually publish the port
- Informs users/tools that app listens on 8000
- Actual port publishing: `docker run -p 8000:8000` or docker-compose.yml

```dockerfile
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

- Command to run when container starts
- `uvicorn`: ASGI server (runs FastAPI app)
- `app.main:app`: Module path : FastAPI instance
  - `app/main.py` contains `app = FastAPI(...)`
- `--host 0.0.0.0`: Listen on all interfaces
- `--port 8000`: Listen on port 8000

**Note**: No `--reload` in production (reload mode watches files for changes; not suitable for production).

### Image Size Comparison

**Single-stage (naive)**:
```dockerfile
FROM python:3.11-full
COPY requirements.txt .

COPY app/ ./app/
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

**Multi-stage (current)**:

- **Total**: ~250 MB (33% of single-stage) ✅

### Versioning Strategy

#### Pinned Versions (e.g., ==0.115.6)
```
fastapi==0.115.6
uvicorn[standard]==0.34.0
```
- **Locked to exact version** — ensures reproducible builds
- Use for: Critical packages (web framework, core deps)
- Benefit: No surprises; same behavior everywhere
- Drawback: Need manual updates for bug fixes

#### Version Ranges (e.g., >=2.10.1,<3.0.0)
```
PyJWT>=2.10.1,<3.0.0
```
- **Allows patches, blocks major version changes**
- Use for: Transitive dependencies, conflict resolution
- Benefit: Automatic security patches
- Drawback: May pull incompatible minor versions

#### Unpinned (e.g., httpx)
```
httpx
```
- **Latest version** — no constraints
- Use for: Transitive deps managed by other packages
- Benefit: Maximum flexibility, latest features
- Drawback: Potential incompatibility

- ❌ No .env file in production
- ✅ Secrets injected at runtime

- ✅ Prevents .env from being copied into image
- ✅ Reduces image size (no build artifacts)
- ✅ Keeps image clean (no git history, test files)

## Troubleshooting

### "ModuleNotFoundError: No module named 'fastapi'"
- Likely cause: requirements.txt not installed
- Fix: `pip install -r requirements.txt`

### Docker image is 500+ MB
- Likely cause: Single-stage build (includes build tools)
- Fix: Use multi-stage Dockerfile (current version does this)

### ".env not found" error at runtime
- Likely cause: .env not copied to local machine
- Fix: `cp backend/.env.example backend/.env` and fill in values

### "Invalid CORS origin" error from frontend
- Likely cause: Frontend URL not in CORS_ORIGINS
- Fix: Add frontend URL to CORS_ORIGINS (comma-separated)

### Container exits immediately
- Likely cause: Missing required environment variables
- Fix: Check SUPABASE_URL, SUPABASE_ANON_KEY, SUPABASE_SERVICE_ROLE_KEY are set
- Debug: `docker logs <container-id>` to see error messages
